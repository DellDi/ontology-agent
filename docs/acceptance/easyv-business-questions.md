# EasyV 业务问题验收清单

首批问题固定于 2026-10-10。目标是验证用户能否查找、比较和判断，不以工具调用成功、返回数量或控件数量代替业务价值。当前验证使用 local-dev（3000）的真实平台快照，不等同于公司当前环境验收。

## 当前业务重点：带业务含义的布局复用（2026-10-10 补充）

用户进一步收敛目标：布局价值与行业、整屏主题、模块目的、指标含义相关。后续优先验证以下三个场景，首批七题及其失败记录保留为历史基线；故障排查与修改历史保留在其他路线，不再占据本阶段业务主线。

| 场景 | 自然问题 | 用户得到什么 |
|---|---|---|
| 重复识别 | 哪些布局重复较多？它们分别用于什么行业、主题？模块和指标是否也相近？ | 重复组、代表原型与可查看的差异；区分骨架重复和业务内容重复，不把重复直接判为低价值 |
| 复用选型 | 我要做医疗运营监测，有哪些现有布局和模块值得复用？为什么？ | 候选承担的业务任务、指标组合及展示方式，说明可复用部分和需要替换的内容；候选缺少行业/主题时如实标明 |
| 适配判断 | 这个布局适合它的主题吗？哪些区域能支持业务判断，哪些需要调整？ | 按整屏目标逐块解释指标与图表、空间/主次安排的关系，列出有依据的疑点；缺少指标口径、真实渲染或用户反馈时保留判断边界 |

“有价值”在本阶段指对某个明确业务任务有用、有解释且有对象可查看的复用候选或改进意见。重复次数证明普遍程度，不证明优劣；生成的模块说明证明设计表达，不证明业务实际成效。暂不输出没有标注依据的通用价值分数。

### 已核对的断点与数据来源

- 当前 `PrototypeStructureParser` 明确排除标题、描述和指标名称，canonical 只写结构、组件类别、几何、绑定 ID 与标题是否存在。V21 的采集元数据也声明 facts 不保存这些文本；Web 对象列表主要以 ID 命名。因此当前不是展示端漏画几行文字，而是业务语义没有进入冻结事实。
- 原始 easyv-ai-java 的 `ScreenPlanningExportAssembler` 将页面 `title`、区域 `businessModule / moduleDescription / themeId / dimensionHint / filterHint / boundMetrics`、组件 `metricName / desc / insight / sceneType / sourceType` 写入原型 JSON。`boundMetrics` 包含指标名称、来源列、聚合规则和单位等。必须通过现有指标 ID 校验绑定，不能只用数组位置或同名指标关联。
- 主视觉由 `MainVisualComponentCodec` 写入页面 `contents`，包含名称、说明及子指标。当前解析器只提取 `blocks` 和其组件；图片中的地图业务语义不能仅靠区域模块补齐。主视觉须与实际 XML 的 Content 节点关联，不能按普通区域造一个虚假对象。
- `StructuredPromptDto.businessContext` 有行业大类/子类、受众，`screenObjective` 有核心目标；代码存在这些字段不等于历史原型 JSON 已保存它们。先核对持久化来源及与当前原型的版本关联；标题可展示为原文，行业推断与源系统明确分类必须分开。
- 上述是当前源代码的生产端契约核对，尚未统计各历史原型字段覆盖。本地快照不含采集原始 JSON，也不能重新物化；现有本地 facts 无法恢复已丢弃的文本。后续需正式采集、物化、发布及快照更新，不让本地运行时直接读取公司源库。

### 最小实施顺序与验收

1. **核对语义覆盖。** 对真实原型检查页面标题、模块说明、指标及绑定、主视觉内容的存在率和来源路径；另查行业/整屏目标的持久化来源。新旧格式缺失如实记录，不从现有几何反推指标含义。
2. **保留并发布业务语义。** 沿现有解析 → 三类 facts → 本体属性 → 对象工具/读取链路增加需要的字段；Flyway、定义、模型和版本发布同步更新。仅保留用于业务解释的明确字段，不暴露原始 JSON、文件内容或任意配置。L1–L4 结构签名保持现有口径，业务文本不混入结构重复判定。语义字段按原权限和冻结版本读取。
3. **贯通展示与分析。** 复用当前画布、组件预览、通用集合/详情：原型显示页面标题与可核验的主题；区域显示模块名称和目的；组件显示指标名称、含义、单位/口径及来源类型。数字、排序、趋势等占位仍表达类型，不用虚构业务值。选中区域的追问带入其模块与指标证据；大量候选继续使用分页集合，不新增行业专用控件。主视觉内容沿既有结构读取与选择链路展示，具体对象建模在覆盖核对后确定。
4. **先交付解释，再做价值校准。** 先用明确模块/指标和布局证据解释“为什么值得复用、哪里可能不适合”。模型推断标明依据和不确定性；正式行业分类与原型设计文案也不保证实际指标正确。再用同版本真实画面和业务评审校准适配判断，不凭重复次数或解析成功评价价值。
5. **按三场景闭环。** 每个候选能下钻到对应模块和指标；比较同时展示结构共性、业务差异及替换限制；结论能回到同冻结版本的具体内容。原样重跑仍相关的 R1/R2、S1/S2；字段缺失或无法绑定的对象不能被模型补成事实。原有过滤规划故障仍是候选查找的前置修复。

| R1 | 我想把现有大屏整理成通用模板。哪些原型的布局重复最多？给我几个值得先整理的候选，并说明它们相同在哪里。 | 降低模板整理与重复建设成本 | 重复口径清楚、有代表原型可查看，说明共同结构；没有重复就如实回答，不把相似当相同 |

## 统一判定

- **支持**：回答业务问题，关键事实对账正确，必要对象/差异可以查看，用户能继续完成该项工作。
- **部分支持**：有可信且有用的结果，但缺少关键解释、对象入口、范围覆盖或决策依据。
- **不支持**：不能完成目标、执行失败、结论失真，或只有字段列表而没有解决问题。
- **样本不足**：现有快照不足以检验某项能力；不以空结果作为该能力通过的证据。

事实正确、任务完成、呈现可理解、证据充分分别记录。支持结论只针对受测问题、账号、版本和数据范围；不要求模型使用指定工具或指定控件，也不人为指定“正确图表”。R2 和 S2 是有上下文的真实追问，若首轮未产生可用候选，则记录阻塞，不为通过而另选无关对象。

### 验证方法与证据边界

1. 首先固定上述自然问题与业务退出条件，通过正常 Web BFF 提交给真实模型执行；没有结构化查询 override 或模型返回 mock。
2. 使用同冻结集、同 EasyV 用户范围的本地 SQL 对账：布局重复组、区域组合交集、解析与流水线状态、失败任务原因/ID。63 个区域是按区域分组同时满足两个组件家族，不是两种组件的混合列表长度。
3. 浏览器实际打开失败、质量检查、澄清与故障排查页面。检查最终回答、可达对象入口和完整用户路径；即使 job completed、事实正确，缺任务入口或质量结论越界也不记完整支持。
4. 本轮只核验结构与过程事实，没有最终大屏渲染评审及可信编辑修订历史。没有把这些数据缺口描述成模型可推断的事实。输出“数据截至当前提问日期”也不能代替快照新鲜时间。

单题实际执行耗时约 R1 33 秒、S1 13 秒、Q1 43 秒、Q2 14 秒、O1 62 秒；批量提交产生的排队时间另记，不能把排队与单次响应混为性能结论。没有以等待较久后收到一张表作为业务通过证据。

## 后续任务顺序

1. **P0：恢复模板查找与组合候选路径。** 修正对象工具过滤的规划描述与准备阶段校验：多值相等匹配使用已有 `EQUALS` 语义，`SET/NOT_SET` 只表示字段是否存在且不接受值；无效规划在事实读取前反馈到现有纠正轮，不把错误过滤悄悄改成另一种含义。修复后原样重跑 R1 / S1，再承接 R2 / S2。
