# D 运营化：首批场景与交付目标（2026-10-22）

目标：让团队知道数据是否经过检查、异常发生在哪里，以及修改后何时能在分析中看到结果。沿用 A/B 的查询、对象、冻结版本与现有发布队列，复用 C 的确认和审计；不另建 Agent、配置平台或调度系统。

## 首批场景

| 顺序 | 真实问题 | 交付 | 退出门禁 |
|---|---|---|---|
| D1 数据健康 | 今天看到的分析使用哪次数据？最近检查失败是否影响已有结果？ | 数据接入增加健康视图，分别展示最近成功检查、已发布版本、最早输入采集时间与最新任务；失败保留上一发布版本及定位编号 | 从全部任务历史取数，超过最近 50 条仍准确；无变化复用更新检查时间但不伪造新版本；未冻结/错误 schema/已撤销版本不算当前发布；空值、零条、失败与未接入明确区分；权限/契约/数据库/页面验证 |
| D2 生成异常巡检 | 新出现哪些生成失败？哪些应用反复失败，值得团队先处理？ | 先复用失败任务与操作记录的既有口径，按冻结版本列出新增失败、重复失败及其对象入口，保留历史对比依据 | 以实际源数据核对任务与应用关联；避免把 Top N 当全量、把一次失败当业务根因。首批先提供按需巡检，持续任务、频率及告警渠道另行明确 |

## 当前 D1 实施边界

- 正式 Java 只读接口 `/api/admin/ingestion/health`，复用现有认证和平台元数据查看权限；Web 透明代理，不访问业务源。
- 每个产品独立查询最新源/物化任务及最近成功物化检查，避免全局最近 50 条窗口遮掉旧成功记录。
- 发布记录来自与当前产品 schema 一致的冻结集，未冻结或含撤销产品的集合不作为已发布版本。输入采集时间沿实际版本血缘读取。
- 未配置新鲜度时限时只展示时间，不自行发明过期阈值或业务质量结论。健康视图不代表 Worker 存活、源站实时可达或完整业务质量认证。
- 页面遵循本轮去框方向，以标题、留白、对齐和明确状态组织，不增加多层卡片。

## D2 按需生成失败巡检（2026-10-23）

- 新增 `/workspace/inspection` 与 Java 只读接口 `/api/easyv/inspection`，从工作台首页进入。Java 使用原 `EasyVScopeResolver` 和 `ObjectQueryPort`，不另写权限过滤或业务源 SQL；无绑定账号明确拒绝。Web 透明代理与服务端页面，不新增 Agent 或调度任务。
- 保持 B 的正式口径：生成任务必须关联同一冻结版本内的未删除应用，普通账号仅见绑定 EasyV 用户的数据。原始快照 8 条失败里 2 条在全部已导入版本中都未找到应用，不能由此判断删除、漏采或源端原因，也不虚构应用归属；正式巡检与现有失败指标统计 6 条，涉及 5 个有效应用，1 个应用有 2 个不同失败任务。
- 按采集时点与集合 ID 选择更早的完整冻结集合，排除不完整/撤销集合，不按发布完成时间对比。同任务 ID 在旧版本也必须通过当前账号权限；旧记录不可见时只标记“首次在可见范围出现”，不能说成刚刚发生。
- 分开“由其他状态转为失败”“首次可见”“前后版本均失败”“无对比版本”。两个版本均失败不证明期间始终失败或根因相同；失败自述保留为线索，不作为已证根因。
- 当前失败集合完整翻页读取后统计，再每页展示 50 条；超过原对象查询可完整读取的边界（最多 10,050 条失败）会整次拒绝，不展示截断统计。重复失败应用按不同任务数排序，只列最高的 10 个，另外保留总数。翻页固定当前集合 ID，刷新才选择最新集合。
