# D 阶段：一批大屏的检查与改进

> 当前目标：2026-10-25 修订，2026-10-31 用户确认继续；目录发起检查与整批续接已补齐本地实现，完整 D 业务验收未通过，尚未发布公司；2026-10-22–23 的数据健康、失败巡检和入口整理保留为已做基础，不作为 D 业务目标完成的证据。

## 要解决的业务问题

团队有一批已有大屏，需要围绕一个明确的使用目的检查内容、选择值得先改的地方并完成改造。当前 B 能查找和诊断对象，C 能对一个普通原型块准备并确认修改；用户仍需自己逐屏提问、记住建议、回找对象和核对结果。

D 的目标是让用户完成同一批对象的 **选择范围与用途 → 找出有依据的问题 → 预览改法 → 逐项确认应用 → 复核实际结果**。交付单位是一批大屏中实际完成的改进，不是报告页、失败条数、任务完成状态或新增控件数量。

典型入口：“这几张大屏要用于运营复盘，帮我按总览、变化和原因检查内容安排，找出值得先改的地方，给我可以确认的改法。”用户从有业务名称的大屏中选择范围，不需要输入应用、任务或版本编号。

## 首批只做这一条闭环

| 用户要完成的工作 | 产品必须交付的结果 | 不可替代的验收依据 |
|---|---|---|
| 定范围、说用途 | 选择有权查看的大屏，明确本次使用目的及必须保留的内容；范围不明确时先澄清 | 后端授权对象与用户选择一致，不能默认检查全平台或漏读后声称全量 |
| 决定先改什么 | 按大屏和具体区域组织少量重点问题，说明当前内容、业务影响、证据与可选改法；重复现象合并说明，共性结论保留逐对象依据 | 可打开对应原型与区域；推断与源事实分开。优先级按对用户目标的直接影响说明，不用失败频次或未校准总分冒充价值排序 |
| 完成修改 | 能力支持的问题直接准备前后预览，在同一工作上下文逐项确认保存；信息不足、无需修改、需要新增指标或跨块重构的问题明确留待人工判断 | 复用 C 的原动作服务；文案与块内图形/排列分别按真实支持范围处理。不以“带入另一个问题”或人工勾选完成替代实际执行 |
| 确认改到了哪里 | 回到原大屏和区域核对实际保存结果，列出本次改变、保留内容以及仍需用户判断的问题；离开后可续接原建议与原动作 | 实时完整读回与确认前后结果一致，目标外内容保持。保存成功不等于业务问题已解决；业务契合由用户核对，不自动认证视觉效果 |

同一批检查复用现有分析会话、执行证据、对象引用与提案/动作，不另建任务调度、审批、指派或通用工作流系统。首批多目标承接已实现，结果仍沿用既有会话呈现；跨屏结果的业务有效性与稳定性待验收。现有查询及 Agent 预算需要明确覆盖边界，不用截断后摘要伪装全量。

## 能力边界和前置条件

- 首批围绕现有主题、模块目的、指标含义、图形与块内组合证据。模型建议必须可回到原对象核对；不能仅凭组件类别、数量或几何推断业务能力缺失。
- 直接改造复用普通原型块现有能力：标题/用途修改，或保留当前全部指标的图形与块内排列调整。新增指标、真实数值绑定、主视觉改造、跨块搬移和最终应用生成均不纳入本批。
- 现有写回只允许绑定的实际 EasyV 应用所有者确认自己的对象；团队查看、平台管理员身份不授予代理编辑权限。首批不扩展团队代改或无人确认的批量写入。
- 分析阶段固定证据范围；准备与保存阶段重新核对实时来源和前态。旧快照发现的问题先检查是否已被人工修正；冲突回到用户确认，不能覆盖新内容或复用过期方案。
- 公司环境写回启用及新适配器发布有独立门禁，不能把本地写回实测称为公司可用。部署、凭据和按对象确认未完成时，不展示虚假可执行动作。
- 当前原型示意不等于最终大屏画面，也没有真实业务数值的完整验收证据；本批不承诺“自动交付验收”或通用质量分。为复核所需的数据更新只是配套条件，不再单独做成 D 的主功能。

## 首批验收与推进顺序

1. **选真实样本并验证可做性。** 从用户有权查看的一批真实大屏出发，先用三张验证范围承接、业务目的与证据覆盖；不预选问题块、不预设诊断答案。对照旧快照与现存改造记录，排除早已修好的旧问题。记录既有人工/逐屏流程的步骤和耗时作为基线。
2. **交付“检查到改法”。** 用户选范围、说目的后，一次获得按对象定位、依据清楚且与实际动作匹配的建议；同一轮可定位到原区域并准备前后预览，不要求用户再拼技术编号或重复上下文。没有足够证据时不强行凑问题数量。
3. **交付“确认到复核”。** 在用户逐项确认和授权目标上完成真实修改，完整读回并与准备结果核对；部分失败或冲突保留已经核实的结果，继续原动作，不重放整批。与第一步同样范围对比用户步骤、耗时及实际接受的改进，不预先宣称节省比例。

D 首批完成需要：至少一批真实大屏走通上述流程；自然发现的问题产生用户认可的改法并至少完成一项必要修改；未选对象、指标绑定及块外内容保持；无需改动/证据不足/无编辑权限/并发改变等情况不产生虚假成功。缺少真实问题时扩大经用户选择的样本，不造问题、不为取得保存证据制造无效改动。

业务验收要回答：“用户是否更快找到值得处理的地方，是否能在这里完成改进，是否确认改到了正确的位置？”接口成功和测试通过是工程门禁，不能单独关闭业务目标。

## 本次修订的取舍

- 停止把数据健康、日志翻译、记录汇总、失败榜单、版本血缘和定时看板继续拆成 D 的主功能。已有接口和运维入口保留，只有阻碍主流程时才补必要能力。

- 模板复用推广、业务评分校准、定时持续检查、团队指派与通知留待真实使用产生需求后再定，不与首批同时铺开。

## 2026-10-25 后台推进：从区域清单到完整指标依据

针对首轮仅深入读取三个区域的问题，Java 复用原 `inspect_block_improvement`，增加一次读取多个真实区域句柄的输入。区域清单连续读取完整后，后台自动补齐全部区域的模块目的、指标含义、口径、单位与当前图形，再交给模型选择值得处理的问题；不再让模型凭剩余调用预算抽样几个区域后结束。每个区域仍走原单块检查与当次授权、冻结版本校验，不另建扫描引擎、数据表或调度系统。

- 单次批量读取最多 50 个不同区域，超出边界明确拒绝；整体仍受原 8 次工具调用、4 次指标查询与 180 秒约束。一次批量工具内部包含逐块数据库读取，不把模型工具调用数说成数据库查询数。
- 完成门禁同时检查区域清单连续覆盖和全部区域的深入读取；只读清单不再通过。提案继续绑定当次已读取的具体区域，后台不接收任意替代对象。
- 修正文案提案的校验缺口：只改标题/用途也必须有源指标名称和含义，不能绕过图形提案原有的语义检查。缺口不使用默认含义补齐。
- 整批深读保留依据供核对，正文不再额外展开整批明细表。批量检查主结果由后台按**实际已校验提案**组织，引用所属屏与区域、原诊断及真实前后内容，不再交给综合模型二次改写；未生成提案的区域不视为检查通过，无提案也不表示无需修改。既有区域浏览入口和逐项预览/确认入口继续使用。
